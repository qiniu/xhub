# XHub 接口完整性与渐进解耦实施计划

[English](../en/interface-integrity-roadmap.md) | [开发指南](README.md)

更新日期：2026-10-24。分析基线：`185726e37e8f456fa62b8df33560cda153b959d8`。状态：分阶段实施；核心契约及未迁移边界见下文，代码提交、合入主分支和生产部署分别验收。

XHub 已在线上提供服务。本计划保留现有功能、页面和兼容入口，先保证接口完整可用、测试结果可信、前后端契约一致，再逐步收拢兼容层和执行链。衡量改善的标准是一次行为修改是否更容易理解、验证和回退，而不是删除了多少行代码。

## 范围与不变量

- 不做功能减负、菜单重组、批量删除旧页面或大规模框架替换；不引入 Python 服务，不拆微服务。
- 不改变用户、SSO、Key、预算规则、模型权限、历史会话标识和已保存的费用快照；确需改变语义时单独提出方案。
- 修正虚假成功和错误输入处理属于本轮范围，但必须记录对现有调用方的影响；不能把错误行为改正伪装成完全无行为变化的重构。
- 每批只迁移一个明确业务边界。保留旧 HTTP 路径和有效请求的兼容性；不同时更换存储结构、协议实现和前端调用方式。
- 准入与目标权限仍由服务端检查；重试不能重复扣费；流已经输出后不能换上游续写；任务创建结果未知时不能盲目重放。
- 数据库提交成功后才能确认用量队列；本地持久化保护不能为了简化异步日志而删除。
- 本文不授权部署、安装新依赖或实施功能变化。后续按仓库 issue 规范复用或补充方案，代码与测试通过后再安排发布。

| 重复解析与客户端 | 管理 JSON 读取、两种前端 HTTP 客户端、Bypass 请求解析存在重复实现 | 合并前核对错误行为、空值语义、上传文件和原始字段保留 |
| 测试门禁 | [quality.yml](../../../.github/workflows/quality.yml) 使用 lint 历史基线；[Vitest 配置](../../../frontend/vitest.config.ts) 在质量模式排除部分已知失败文件 | 对外报告实际执行范围、排除、skip、首次失败与重跑结果 |

这些事实不等于全部接口不可用，也不等于全部测试虚假。产品中的“测试连接”接口假成功，与单元测试合理使用 mock，是不同问题。

“未知”“部分验证”“已验证”“明确不支持”必须分别记录。未知能力不能自动标成支持，也不能未经契约决策就改变原有请求处理。每个推断必须给出证据入口、待验证事项及验证方法；没有证据时不承诺性能改善、供应商兼容或安全性。

## 接口完整性的交付标准

建立一份可审查的接口清单。首批从一个业务域开始，逐步覆盖所有正式开放入口；兼容别名、原生入口和目录兜底入口都要登记，不以新增小子集代替全量分母。

每项至少记录：

| 类别 | 必需内容 |
| --- | --- |
| 标识与实现 | method、path、业务域、handler、兼容别名、实现状态、契约版本 |
| 请求 | 认证方式、角色与租户范围、字段类型、默认值、缺省与 null 与零、未知字段、请求大小 |
| 响应 | 成功正文、错误正文、状态码、分页、相关响应头；禁止仅写通用 200 |
| 业务结果 | 存储变化、运行时生效点、是否触达上游、费用、幂等、撤销与清理 |
| 证据 | 单元、真实 HTTP regression、用户路径 E2E 的用例及报告；未覆盖的供应商行为 |

一次“保存成功”必须能读取真实状态，并在相关运行时路径观察到效果；如果接口只负责保存配置，应明确说明尚未验证连接。“测试成功”必须说明完成了结构校验、网络连通还是实际协议调用。

既有“测试连接”或“测试提示词”承诺实际执行时，仅把文案改成“结构校验成功”不能算完成。要登记其实际承诺并补齐调用、失败和清理验证；暂时只消除假成功时，该功能完整性仍标为未完成。

既有请求语义优先从实现、调用方、回归和已确认的产品规则共同核对。不能仅凭旧类型文件、上游文档或模型推测替后端补出响应字段。契约冲突形成单独决策记录，不靠修改测试期望悄悄接受。

## 自动接口文档与契约方案

### 建议的试点

先选用户或 Key 管理的一组创建、读取、更新、删除操作，保留现有路由和 handler。用 OpenAPI 3.0.3 做工具兼容性试点；工具版本锁定并验证后再确定格式与目录，以下路径仅作建议。

~~~text
api/contracts/<domain>.yaml  权威契约
  -> Go 请求和响应类型     逐接口接入现有 handler
  -> TypeScript 类型       迁移对应的前端调用
  -> 静态 API 文档         本地和 CI 构建产物
  -> 真实 HTTP 契约验证    检查真实响应及错误
~~~

契约初稿来自已确认的业务行为；迁移后契约成为该域唯一的接口定义来源。业务逻辑仍手写，生成代码不是业务实现。未迁移接口保留旧调用及类型，逐域登记，不直接覆盖整份 `schema.d.ts`。

### 工具分工

| 工具 | 计划用途 | 边界 |
| --- | --- | --- |
| [oapi-codegen](https://github.com/oapi-codegen/oapi-codegen) | 从契约生成 Go 类型；试点评估与现有 Gin handler 的衔接 | 首批不切换整个路由框架；生成器不是鉴权和业务校验实现 |
| [openapi-typescript](https://openapi-ts.dev/introduction) | 从同一契约生成前端类型，沿用现有客户端生态 | 类型通过不能证明运行时响应正确 |
| [Swagger UI](https://swagger.io/open-source/swagger-ui/) | 渲染自动接口文档，供本地查看和测试环境调试 | 文档展示不等于接口已实现；不默认向生产发送请求 |
| [swaggo/swag](https://github.com/swaggo/swag) | 作为 Go 注释生成文档的备选方案 | 当前主文档描述 Swagger 2.0；与 OpenAPI 3 工具链的衔接需验证，不同时维护两套权威来源 |

不需要为了文档增加外部服务。依赖与静态资源固定版本，文档示例不带真实凭据；初期不恢复 `/openapi.json`，也不默认启用生产写操作的在线调试。若后续需要控制台内文档，单独验证入口权限、地址与请求目标。

CI 逐域增加契约语法检查、生成结果差异检查、破坏性变更检查和真实响应验证。旧接口中已合法的未知字段、数字字符串等兼容规则必须先登记；不能因生成了类型就一次性加严格中间件拒绝所有旧请求。

### 原生与流式接口的特别边界

OpenAPI 描述入口、认证、错误包络和可描述的字段；它不能单独证明 SSE 事件顺序、首字节后失败、断流结算、工具调用或历史续接正确。

原生请求保留未知字段、数值精度、multipart 文件内容和协议事件。管理 API 可以逐步使用严格类型，原生供应商载荷不能统一反序列化后丢弃未知字段。跨协议只转换明确支持的语义；不把本地 fixture 的兼容性结论推广为所有供应商都支持。

## 测试真实性规则

### 各层能证明什么

| 层级 | 真实边界与用途 | 不得声称 |
| --- | --- | --- |
| 单元与组件 | 解析、权限决策、转换、状态机；允许可控 mock 和失败注入 | 供应商连接成功或真实数据库事务完成 |
| 后台 regression | 真实 HTTP handler、隔离 PostgreSQL、实际持久化与准入；本地协议上游可记录请求和注入故障 | 本地上游通过等于 Fenno 或其他真实供应商通过 |
| 浏览器 E2E | 真实页面到网关再到数据面，断言持久化和上游结果；关键管理 API 不用页面拦截伪造成功 | 只点按钮、检查 toast 或得到 200 就完成业务验收 |
| 真实供应商验收 | 明确端点、型号、协议、时间、预算上限和专用测试身份的小范围验证 | 一次成功证明整个供应商或全部模型兼容 |

真实供应商验证单独安排，不进入默认离线套件，不借用真实员工账号或记录聊天内容；不存在凭据时明确列为未覆盖，不生成“通过”结果。

现有浏览器套件使用生产构建的控制台、真实网关 handler 和本地依赖夹具；企业模式会运行测试专用网关入口。它不等于正式 Docker 镜像启动验证，也不证明真实七牛 SSO、外部 TLS 或反向代理可用。这些部署边界分别保留验收项。

### 必须覆盖的错误与清理

- 保存流程覆盖非法 JSON、字段缺省与 null 与零、权限不足、资源不存在、数据库失败，以及读回和运行时效果。失败时验证没有伪造对象、没有非预期修改。
- 连接测试用本地 HTTP fixture 验证实际请求发生；分别注入 401、403、429、5xx、超时、无效正文。若功能只是结构检查，明确报告检查级别，不能显示连接成功。
- 推理覆盖 JSON 与 SSE、同协议与跨协议、工具与图片、父响应与旧会话、取消与断流；检查客户端结果、上游尝试次数、日志关联和费用一致。
- 流式响应提交后，HTTP 状态可能已固定为 200；流内失败必须独立记录，不改写成可重新发送 HTTP 错误的假象。
- 单元和 regression 的关键失败用例应先在未修复实现上复现。采用局部、可撤销的失败注入验证测试确实会失败，不在生产或共享数据库做破坏实验。
- 不用重跑隐藏首次失败，不通过扩大排除名单使 CI 变绿。必需用例缺失、零匹配、必需依赖 skip 或清理失败必须阻止该批验收。
- 隔离 schema、独立 Redis 命名空间与测试资源在成功和失败路径都要清理，并保留清理结果；严格模式还需检查非法 DSN、连接失败与删除失败分支。

现有严格回归与 E2E 隔离能力优先复用。lint 基线、测试排除逐项登记归属和恢复条件；修改涉及被排除文件时须单独执行，并报告其结果。

## 解耦边界

保留现有模块化单体。先调整模块内部职责，再考虑移动目录；不增加另一个统一框架。

| 边界 | 负责 | 本轮禁止扩张 |
| --- | --- | --- |
| HTTP 与兼容适配 | 旧路径映射、请求解析、响应包络 | 不再按路径猜测并伪造业务成功 |
| 领域服务 | 资源校验、授权、事务与业务结果 | 不直接接管供应商协议和 SSE |
| 配置与路由 | 编译有效配置、筛选候选、形成尝试计划 | 不重新定义身份、预算或历史所有权 |
| 协议适配 | 原生载荷保留、明确的跨协议转换 | 不写身份库或自行结算 |
| 执行器 | 超时、取消、重试边界和输出生命周期 | 不逐个承载供应商字段规则 |
| 账务与观察 | 用量、价格快照、日志与幂等持久化 | 不改变上游响应语义 |

兼容层逐路由委托明确服务，保持已有响应形状。先迁移一个真实使用的管理资源，核对保存、读取、失败与权限，再扩展下一种。默认兜底的退出要有明确覆盖清单，不能大范围改成 404 或删除旧接口。

标准和 Bypass 共用请求生命周期、诊断和结算组件，但保留历史、护栏、异步任务和重试差异。每次重试复核目标权限是必要逻辑，不能当重复检查删除。

## 分阶段实施

阶段按完成条件推进，不承诺日历工期。阶段 1 的明确 Bug 可与阶段 2 的离线工具试点并行；同一接口的迁移必须等其基线与错误行为明确后开始。

| 阶段 | 交付物 | 完成条件 | 回退边界 |
| --- | --- | --- | --- |
| 0 建立基线 | 核心入口清单、兼容别名、现有用例与排除清单、最小重现 | 每个首批接口均有真实 handler 与调用方证据；完整性缺口明确 | 仅清单和测试，不改生产行为 |
| 1 修正错误语义 | 失败先红后绿的测试；存储错误处理、JSON 校验、探测检查级别修复 | 故障注入能阻止假成功；成功路径、权限、i18n 与清理通过 | 独立修复提交，无数据迁移；不得把回滚假成功当默认修复方案 |
| 2 建立契约试点 | 一个领域的 OpenAPI、Go 与 TS 类型、离线文档、契约 CI | 可重复生成且零差异；真实 HTTP 正反例符合契约；旧客户端仍可用 | 不启用新线上文档路径；保留现有 handler 和未迁移调用 |
| 3 扩展核心契约 | 用户、Key、模型、日志等逐域迁移；共用前端错误策略 | 对已迁移集合达到逐项覆盖；总清单显示未迁移项，核心用户 E2E 通过 | 逐域回退，不替换整份 schema 或全部客户端 |
| 4 收拢兼容层 | 一种资源一个明确服务边界，移除已被替代的重复实现 | 旧 URL、权限、响应、事务、错误完全有回归证据 | 保持存储与外部 API，适配器可单独恢复 |
| 5 整理执行链 | 先去重 Bypass 解析，再统一配置快照与尝试结果，最后提取生命周期 | 协议、流、历史、日志、费用与重试矩阵通过；未知字段不丢 | 每次只改一个边界，候选灰度保留旧路径；不破坏历史格式 |

建议首批 PR 顺序：基线与反例测试 → 持久化错误及严格 JSON → 探测接口真实语义 → 用户或 Key 契约试点 → 对应前端迁移 → 一种兼容资源服务化。执行链整理放在这些结果稳定之后。

“先红后绿”发生在同一修复 PR 的验证过程中，保留修复前失败与修复后通过的证据；不先合入故意失败的测试。独立基线 PR 只增加通过的行为基线和缺口记录，也不通过 skip 新反例制造绿色。

已有既定行为的错误用 BUG 跟踪；新增文档入口、检查级别语义或契约流程用 Proposal；跨模块方案按仓库规范使用 Architecture-Design。本文不代替这些具体变更的验收记录。

实际阶段 2 首个试点选择供应商管理（Proposal #149），随后扩展用户、Key、模型与端点（#159）。第三阶段核心收尾以 #161 的 48 个操作为边界，包含日志/日报、密码重置和 Key 生命周期；详见[核心契约收尾](core-contract-completion.md)。#162 合入已关闭的 #160 来源分支，未随 #160 进入 main，因此需重新向 main 提交收尾代码。最终完成条件是收尾提交进入 main、契约兼容和真实测试全部通过，而不是 PR 显示 merged。外围接口仍单列未迁移，不计入核心完成。

## 第四阶段首批：供应商配置服务

[提案 #168](https://github.com/qiniu/xhub/issues/168) 先拆供应商这一种资源，不代表第四阶段全部完成。

- `family` 保留旧 URL 解析、管理鉴权、JSON 校验、HTTP 包络和错误映射。
- `internal/gateway/suppliers` 负责配置 CRUD、补丁合并、缺省字段和响应脱敏；仅依赖窄 KV 接口，不依赖 HTTP 或数据面。
- 共享秘密字段识别移至 `internal/credentialfields`，搜索配置仍保留自己的递归合并规则。
- 存储 kind/ID、同名覆盖、缺失更新 upsert、非事务批量删除、扩展/null/零值均保留；不迁移表，不增加缓存。
- 模型执行链继续读取原 `credentials` 数据。真实回归验证地址/Key 轮换、掩码保留、上游 401、恢复和费用；中英文 E2E 验证页面编辑到推理全过程。
- 回退此批服务和适配器提交即可恢复旧实现，无数据库回滚。此批只提 PR，合并与部署另行决定。后续资源逐个迁移，原生协议执行链不在本批范围。

## 每批变更的验收与发布

每批报告必须列出提交、变更接口、旧行为与新行为、测试层、命令、pass/fail/skip/排除/重跑数量、报告路径、清理结果和外部依赖边界。没有运行的测试写“未运行”，没有匹配到用例不能写“通过”。Go 顶层用例与子用例分开计数，报告只保存请求 ID 和脱敏结构，不记录真实 Key、密码或聊天正文。

至少保留下列用户路径，按本批影响选择执行：

| 用户路径 | 必需断言 |
| --- | --- |
| 登录后进入模型与 Key 页面 | 有效会话保留；真实失效退出；自定义 Key 错误不注销登录 |

| 保存模型或连接配置再调用 | 选中端点和协议真实生效；失败可定位；凭据不泄漏 |
| 旧会话继续与流式调用 | 工具、图片、历史归属、错误和用量一致；不重放已输出的流 |
| 查看日志与用量 | 同一请求关联所有尝试、上游错误和最终结果；费用按原快照解释 |

涉及页面时同时验证中文与英文、动态参数和错误状态；示例提示词使用英文，保留用户原始输入。发布前在测试环境验收；涉及执行行为的变更先对受控账号灰度，不因文档或构建通过自动全量部署。观察协议错误、登录失败、计费差异及延迟，阈值由阶段 0 基线确定，不凭空填写。
