# XHub issue 写作规范

让没有参与聊天、不了解历史调试过程的同事，看完开头就知道：谁遇到什么、要改变什么、怎样才算完成。默认中文，保留协议字段、模型 ID、命令和用户原始输入；示例提示词使用英文。

## 分类与标签

| 类型 | 标题 | 标签 | 必须说明 |
| --- | --- | --- | --- |
| 已有行为不符合预期 | `Bug: 具体场景与错误结果` | `BUG` | 现象、复现、影响、证据、验收 |
| 新功能或功能微调 | `Proposal: 希望实现的具体行为` | `feature` | 动机、方案、例子、验收、兼容影响 |
| 全局流程、跨模块规则、架构调整 | `Proposal: 要统一或调整的流程` | `Architecture-Design`；同时涉及功能则加 `feature` | 职责边界、流程、失败处理、兼容迁移、取舍 |

- 所有功能调整，包括小范围默认值、交互、配置行为的微调，在实现前都应有 proposal。已有 proposal 覆盖相同范围时更新复用，不为每个提交重复开 issue。纯恢复既定行为的 bug 修复不额外复制一份功能提案；如修复引入新行为或全局规则，补充关联 proposal。
- `Architecture-Design` 与 `feature` 不是互斥标签。不要把所有 bug 或所有多文件改动都标成架构设计。
- 上游问题仍可跟踪，但正文标明“上游跟踪”及对照依据；原因未确定写“待定位”，不能因为出现 HTTP 4xx/5xx 就归因 XHub。
- 保留仓库已有相关标签，不随意删除。缺少所需标签时，在已授权整理仓库的范围内创建；没有权限则报告，不替换为近似标签。
- 优先级写在状态行：P0=广泛中断或严重数据/安全事故；P1=核心路径错误且无合理绕行；P2=局部故障或有绕行；P3=一般改善。必须写影响依据；沿用已有优先级，缺乏证据时不擅自升级。

## 写作与执行

1. 读取目标 issue、相关评论、已有 proposal/PR 和标签，搜索重复项。区分既有证据、本次验证和待验证假设。
2. 一条 issue 对应一个可验收的结果。设计总议题可关联子议题，正文避免堆积不相关问题。
3. 标题直说行为，不堆叠优先级、日期和技术标签。正文先写一句概要和状态，再按下方模板展开。小提案通常 200～500 个中文字即可；复杂设计以可评审为准，不受字数限制。
4. 不写“增强稳定性”等无法验收的目标。用一个具体的前后对照说明变化；未决定的选项写在“待决策”，不伪装成已批准方案。
5. 正文保留当前结论和足够复现证据；长日志、调用矩阵和过程记录放关联评论或折叠区。整理旧 issue 保留编号、原证据链接、处理状态和未验证边界，不因改写而关闭问题。
6. GitHub 中不要放密码、Token、API Key、真实用户请求正文或内部凭据。代码证据优先使用带提交号的永久链接；仅在本机的报告不能作为其他同事唯一可读的证据。
7. 用户授权创建/整理 issue 时直接执行对应发布或编辑；若只要求草稿则不发布。发布前检查目标仓库、秘密信息、标签和正文，发布后读回核对；结果不明先查询，避免重试产生重复 issue。错误持续且无安全恢复方式时停止并说明。
8. 实现 PR 关联 proposal/bug。关闭前按 issue 验收条件核验证据，说明验证版本与范围；合并、部署、线上验证是不同状态，跳过测试不计通过。本次只改文案时不宣称重新复现或修复。

## Bug 模板

```markdown
一句话说明用户可见的故障和影响。

状态：待定位 / 已确认 / 上游跟踪 / 暂缓。优先级：有依据时填写。

## 复现与现象
1. 环境、模型、协议和必要前置条件。
2. 最少操作或脱敏请求。
3. 实际结果；预期结果。

## 影响与证据
影响范围、已确认对照、证据链接；明确未知项。

## 下一步与验收
- [ ] 修正后用户可观察的结果。
- [ ] 相关正常与失败路径验证。
```

## 功能 Proposal 模板（微调同样适用）

```markdown
## 概要
为谁增加或调整什么行为。

## 背景
现在哪里不好用，为什么需要改变。

## 方案
明确入口、操作或输入、输出和默认行为。
例子：现在……；调整后……。

## 验收条件
- [ ] 用户能完成……。
- [ ] 异常时表现为……。

## 兼容与范围
对现有用户、配置、接口的影响；不影响则说明依据。
有未决选择时补“待决策”，没有则删除该节。
```

## 架构 Proposal 补充项

在功能模板中按实际需要补充：
- 现有流程与拟议流程，各模块负责什么；边界明确时再给接口或数据示例。
- 全局规则及失败路径（如重试、回滚、取消、状态恢复）。
- 迁移和发布顺序、旧行为兼容方式、验证覆盖范围。
- 有实际取舍的备选方案及选择理由；尚未决定的内容单列。

不是所有架构提案都必须画图，也不要为凑结构填写空泛内容。
